For decades the specification was the draft: you wrote it to align, then filed it away while the real work, coding, began. GenAI inverts that hierarchy. The hinge of the talk. Two things you control: the precision of your intent (what you ask) and the state of the agent's context (what it can hold). Act one was intent: the spec is the deliverable. 07 · The Constraint

Context rots

source: Chroma, “Context Rot” (2025)

Every model degrades as the window fills. Output quality is a function of what is in context, so curate it ruthlessly.

The catch. This chart (a simple repeated-words task scored by Levenshtein distance) shows every model, Claude Sonnet 4, GPT-4.1, Qwen3-32B, Gemini 2.5 Flash, falling off as input length grows. A big context window is not a big working memory. More tokens in the window means more distraction and more rot. So the practical skill is managing what goes into the window, which leads to the technique on the next slide.

Do not pile everything into one window. Delegate to sub-agents: they spend their own context and hand back only the answer.

Two ways to spend a context window. Left (dumb): one agent does every read, search and write in a single window; it blows past 50% and the lower half is context rot, where the model gets worse as the window fills (the previous slide). Right (smart): the main agent is an orchestrator. It delegates heavy work via Task() to a sub-agent running in its own fresh context; the sub-agent does all the reads, searches and writes there and hands back only the distilled result. The main window stays lean, so quality holds. This is the single most useful habit from the talk, and the closing slide shows it in code.

GitHub Copilot

A skill is a markdown file you invoke by name: a /slash in Claude Code; Copilot has no slash, so it matches your prompt to the skill’s description.

A skill is a modular unit of know-how: one markdown file with a description, a system prompt, a tool allow-list, and a model. The description does double duty: it documents the skill and it is how tools without slash commands find it. In Claude Code you invoke a skill with a first-class slash command, like /flow:research-requirements. GitHub Copilot has no first-class slash invocation; you hint the skill inside a prompt and Copilot matches that prompt against the skill's description field to decide whether to run it. Same file, two invocation paths, which is why migrating commands to skills makes them portable. Adding or swapping a skill is a one-file change, no redeploy.

A whole workflow, distributed like a dependency: install the plugin on Claude Code or Copilot, then /flow:init wires it to your project: tracker, cross-review, and AGENTS.md.

Because skills are just files on the open standard, a whole set ships as one plugin. In Claude Code: /plugin marketplace add corticalstack/flow, then /plugin install flow@flow. In GitHub Copilot CLI: gh skill install corticalstack/flow. Same SKILL.md files, both tools. Then /flow:init is an interactive wizard, run once per project: it creates AGENTS.md from the template, asks which tracker you use (GitHub, Azure DevOps, or none) and writes .claude/tracker.json, and optionally sets up cross-vendor review profiles. It never overwrites existing files. The point: an opinionated engineering workflow now installs and bootstraps like a dependency, not a copy-paste.

The repo carries the baseline + config (AGENTS.md, CLAUDE.md, .mcp.json, gitignored).
The plugin carries the workflow itself: skills, agents, tracker adapter.

Flow installs as a plugin: /plugin install flow@flow puts the workflow skills, the sub-agents, and the tracker adapter (tracker.sh plus a bin/tracker wrapper on PATH) under ~/.claude/plugins/marketplaces/flow/, not in your project (a plugin-installed repo has no ./.claude/skills/ of its own). The three gitignored files all live under .claude/: tracker.json picks the tracker backend (written by /flow:init); skills/cross-review/profiles.json holds the cross-review endpoints and model names; settings.local.json is personal per-machine settings (mainly the Bash allow/deny list). Any hooks (block .env writes, auto-format) live in your own project .claude/settings.json, not the plugin.
13 · The Workflow

Stage the work, clear the context

AGENTS.md precondition (always loaded): on main? → git checkout -b feature/<id>-<slug> first
/flow:research-requirements or /flow:research-codebase new / existing
research.md ⌫ /clear
/flow:create-plan
plan.md ⌫ /clear
/flow:implement-plan
diff ⌫ /clear
/flow:validate-plan ↻ fail → re-implement
/flow:commit → push → draft PR → /flow:describe-pr → ready → @claude review → ✓ merge
changes requested? ↻ /flow:handle-pr-feedback → re-review

Each stage runs in a fresh context: the artifact (spec, plan, diff) carries state forward, then /clear wipes the window so the next stage starts lean.

The skills now install as the Flow plugin, so they invoke under the flow: namespace. An always-loaded AGENTS.md precondition comes first: before any file-writing step the agent checks the branch and, if on main, proposes and runs git checkout -b feature/<id>-<slug>. Then the skill pipeline. Research forks by context: /flow:research-requirements for a new feature or /flow:research-codebase for an existing one, both writing a research doc into flow/research/. /flow:create-plan reads it and writes plan.md; /flow:implement-plan reads the plan and writes code; /flow:validate-plan checks the work and loops back to /flow:implement-plan on failure. Each stage writes a markdown artifact reloaded as the next stage's context, while /clear (a built-in, not a Flow skill) wipes the chat between stages, so the file carries the state and the window stays lean. Then ship: /flow:commit, push, open a draft PR, /flow:describe-pr writes the description and updates the PR, mark it ready, then you @-mention claude in the PR to review; approved merges, changes-requested runs /flow:handle-pr-feedback and re-reviews. The framing: a deterministic workflow of short-lived agent segments; the orchestrator picks the path, the model only picks the next tool. Branch creation lives in AGENTS.md, not in any skill, so skills stay single-purpose and the rule stays tracker-agnostic.

The trail is the state. Resume, hand off, or switch tools by reading the files; the chat is disposable.

The flow/ directory is the durable trail. /flow:research-requirements and /flow:research-codebase write flow/research/; /flow:create-plan writes flow/plans/ which /flow:implement-plan reads; /flow:describe-pr writes flow/prs/; /flow:cross-review writes flow/reviews/; /flow:create-handoff writes flow/handoffs/ which /flow:resume-handoff reads. All markdown. The convention is that the next stage reads the previous stage's artifact in a fresh context, never raw chat history. That is the staging discipline AGENTS.md encodes, and it is what makes handoff and tool-switching possible.

Documentarian principle: describe what exists. Never critique, never propose. Findings, not opinions.

Read-only sub-agents run in parallel, each in its own context window, so the orchestrator never loads raw files: it gets synthesised findings, not opinions.

The research phase fans out to specialised, read-only sub-agents: a codebase-locator finds where things live, a codebase-analyzer traces how they work. Running them in parallel is a context strategy: each has its own context window, so the orchestrator only ever receives synthesised findings, never large volumes of raw file content. The documentarian principle is the key constraint: every agent describes what exists and never critiques, suggests improvements, or proposes refactors. That keeps research factual and stops it bleeding into premature design. Findings land in a research doc with concrete file paths and line numbers that the plan then references directly.
16 · The Adoption

Two ways in

Greenfield · structured blank page
  • Iterate on the spec, not the code
  • Cycles compress from weeks to days
  • Stakeholders clarify intent up front, when it is cheap to fix
vs
Brownfield · legacy, no specs
  • Specify every new feature before building it
  • Bootstrap specs from the existing code, module by module
  • The codebase grows an intentional memory it never had

New project: iterate on the spec, not the code.
Legacy: specify forward, feature by feature, until intent is documented.

Most organizations are not on a blank page. Greenfield: describe what you want unconstrained by legacy, iterate on the spec, and the hardest conversations, between developers and business stakeholders, happen at the start of the cycle when misunderstandings cost little. Brownfield is harder but more transformative: do not rewrite; adopt spec discipline incrementally, feature by feature, bootstrapping specs from existing code until the codebase carries documented intent that makes agents far more effective.
